# RAID1 на рабочем компьютере

Я хочу использовать RAID1 для рабочего компьютера, чтобы в случае отказа одного
из SSD дисков моя работа не остановилась.

На сегодняшний день у меня только один SSD диск на 2TB. Покупать еще один
такого же размера мне кажется не целесообразно. Можно купить SSD на 1TB и таким
образом иметь 1TB в raid1 массиве и еще один 1TB не защищенных raid массивом.

Проект, который я хочу реализовать, будет состоять из двух частей. В первой
части я создам RAID1 массив для защиты `/home`, а корневая файловая система
останется вне RAID массива. Это связано с тем, что загрузка операционной
системы с программного RAID массива требует дополнительной настройки initramfs,
загрузчика и ESP. Эту задачу я решу во второй части проекта. При работе над
первой частью нужно сразу учитывать будущий перенос корневой файловой системы в
RAID массив, чтобы обойтись без существенной переразметки дисков и миграции
данных во второй части.

# Part 1

Предположим, что в моем распоряжении 2 SSD диска:
* /dev/vdb - 2TB
* /dev/vdc - 1TB

`/dev/vdb` - это основной диск, на котором сейчас находится загрузчик и
установлена операционная система:
* /dev/vdb1 - 512MiB ESP (EFI System)
* /dev/vdb2 - Linux filesystem

Т.к. я хочу 1TB этого диска поместить в raid массив но нужно будет иметь 3 раздела:
* /dev/vdb1 - 512MiB ESP (EFI System)
* /dev/vdb2 - ~1TB Linux RAID
* /dev/vdb3 - Linux LVM (for unimportant data)

Поскольку я хочу защититься от потери любого из дисков, то на каждом из дисков
должен быть EFI раздел. Это означает что и на диске /dev/vdc должно быть 2
раздела:
* /dev/vdc1 - 512MiB ESP (backup EFI System)
* /dev/vdc2 - оставшееся пространство (~1TB за вычетом ESP), Linux RAID

Поскольку ESP занимает 512MiB, раздел `/dev/vdc2` будет немного меньше 1TB.
Сначала нужно создать `/dev/vdc2`, а затем создать `/dev/vdb2` с точно таким же
количеством секторов (либо немного меньше). Размер RAID1 будет определяться
размером меньшего из двух разделов.

Разделы `/dev/vdb2` и `/dev/vdc2` нужно объединить в RAID1 массив (зеркало):
```bash
$ mdadm --create /dev/md0 \
    --bitmap=internal \
    --level=1 --raid-devices=2 \
    /dev/vdb2 /dev/vdc2
```

Далее создадим два physical volume под управлением LVM:
```bash
$ pvcreate /dev/md0
$ pvcreate /dev/vdb3
```

Объединим их в одну группу, чтобы в будущем иметь возможность перемещать данные
между ними при работающей системе:
```bash
$ vgcreate vg0 /dev/md0 /dev/vdb3
```

Внутри `vg0` уже создадим логические разделы, которые отформатируем с помощью
файловой системы:
```bash
# raid protected logical volume
$ lvcreate -L 128G -n lv-system vg0 /dev/md0
$ lvcreate -L 256G -n lv-home vg0 /dev/md0

# non-raid logical volume
$ lvcreate -L 256G -n lv-data vg0 /dev/vdb3
```

Создадим файловую систему на этих логических разделах:
```bash
$ mkfs -t ext4 /dev/vg0/lv-system
$ mkfs -t ext4 /dev/vg0/lv-home
$ mkfs -t ext4 /dev/vg0/lv-data
```

## ESP

Чтобы иметь возможность загрузиться после отказа любого из SSD дисков, нужно на
обоих SSD дисках иметь раздел с ESP (EFI Partition) на котором будет находится
shim/GRUB. Также в UEFI нужно создать загрузочную запись для каждого из ESP
разделов. Переодически синхронизировать ESP разделы после обновления GRUB или
shim.

Важно проверить загрузку системы с отключением каждого из SSD дисков, чтобы
убедиться в работоспособности этой схемы.

## Advanced details

Если `/dev/vdb` выйдет из строя, то `/dev/vdb3` станет недоступен, а `vg0`
перейдет в partial state. Логические тома `lv-system` и `lv-home` останутся
доступны через `/dev/md0`, но `lv-data` будет недоступен. Чтобы отсутствие
необязательного логического раздела `lv-data` не останавливало загрузку
системы, для него нужно использовать опцию `nofail` в `/etc/fstab`:

```fstab
/dev/vg0/lv-data /data ext4 defaults,nofail 0 2
```

Сервисы, необходимые для загрузки и работы системы в degraded state, не должны
зависеть от данных на `lv-data`.

### Конфигурация MD в initramfs

Если корневая файловая система расположена на MD RAID, массив должен быть
собран еще до того, как станет доступен настоящий корневой раздел. На этом этапе
Linux работает из временной файловой системы initramfs.

Изменение `/etc/mdadm/mdadm.conf` обновляет конфигурацию только на настоящей
корневой файловой системе, которая еще недоступна во время ранней загрузки.
Поэтому после изменения конфигурации MD нужно пересобрать initramfs и скопировать
в него актуальную конфигурацию:

```bash
$ sudo update-initramfs -u -k all
```

Параметры команды:

* `-u` — обновить существующие образы initramfs;
* `-k all` — обновить образы для всех установленных ядер.

Проверить наличие `mdadm` и его конфигурации в текущем initramfs можно так:

```bash
$ lsinitramfs /boot/initrd.img-$(uname -r) | \
    grep -E 'mdadm|mdadm.conf'
```

Если корневая файловая система находится вне RAID, а `/dev/md0` используется
только для данных, сборка массива не требуется для монтирования корневой
файловой системы. В таком варианте обновление initramfs для загрузки системы не
обязательно: массив может быть собран уже после перехода на настоящий корневой
раздел.
